# React and Django migration

The browser now runs React components built by Vite. The existing CSS, icons, form layouts, labels and route names are retained. Django/Waitress owns the public API, authentication, user administration, audit queries, document authorization, uploads, corrections and asset delivery. PostgreSQL uses the existing schema; no account or document conversion is required.

`run_portal.py` supervises Django and `ocr-worker.mjs`. The worker binds only to loopback, authenticates every request with a private token generated by the supervisor, and retains the existing RapidOCR, Tesseract, form extraction, checkbox, verification and Excel algorithms. It does not serve browser routes. The worker uses PostgreSQL's existing advisory lease and recovers queued originals after restart.

## Compatibility details

- Existing sessions, ownership checks, first-login password changes, CSRF tokens and retention settings remain compatible.
- Existing Node Argon2 hashes can encode parameters in `m,p,t` order. Django normalizes the encoded parameter order when checking a password; it does not modify the salt, digest or stored account.
- Corrections are validated and persisted by Django; the private worker runs the original automatic verification rules. Saved corrections remain distinct from source-confirmed readings.
- Original PDFs and completed page images remain in PostgreSQL. Temporary OCR images are disposable.
- JSON/text exports preserve the existing data shape; Excel generation retains ExcelJS and the existing worksheet builder.
- The internal worker port defaults to public `PORT + 2`; it is never exposed by the Docker image. Keep one application instance per database.
- Legacy `public/*.js` files remain as historical comparison/test references, but Django serves the compiled React frontend. It exposes only the preserved CSS/icons from `public`.

## Build and run

Install JavaScript dependencies with `npm ci` and Python dependencies using `requirements.lock.txt`. Run `npm run build`, then `npm start` or `python run_portal.py`. Rebuild React and restart the server after frontend changes because WhiteNoise inventories static files at startup. Existing migration/bootstrap CLI commands remain available.

The production package includes `backend`, compiled `frontend/dist`, the OCR worker, Python helpers, and the existing offline models. Docker builds the frontend with development dependencies, then removes those dependencies from the runtime installation.

## Verification

Use the isolated `.env.qa` database and port 4318 for integration tests. Never run QA tests against the live database.

- `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`.
- `.venv/Scripts/python.exe manage.py test backend.tests` on Windows.
- `.venv/Scripts/python.exe -m unittest discover -s test -p 'test_*.py'`.
- `node scripts/test-react-migration.cjs`: upload confirmation through OCR, corrections, verification, exports, persistence, filtering and responsive routes.
- `node scripts/test-migration-parity.mjs`: compare complete page data, verification results (excluding timestamps), and workbook values/formats against the original application's synthetic baseline.
- Existing authentication, account lifecycle, audit, security, isolation, browser, cancellation and recovery suites remain applicable. `scripts/restart-test.ps1` recognizes the Django process and only targets the isolated QA port.

Synthetic baselines are digital, skewed and blank legacy claim forms. Equality on these fixtures is not a claim of perfect extraction for every PDF. Local validation does not replace Linux container qualification, a new image security scan, or AWS staging acceptance. No production deployment is included in this migration.
